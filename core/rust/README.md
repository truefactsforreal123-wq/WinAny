# Native core (foundation only)

Build: `cargo build --manifest-path core/rust/Cargo.toml`. The `remote_core` cdylib exports `remote_core_call(const char*) -> char*` and `remote_core_free(char*)`. The caller supplies NUL-terminated UTF-8 JSON and must free the returned string once. Responses are `{ "ok": true, "result": ... }` or `{ "ok": false, "error": ... }`. Requests must be bounded by the trusted caller; the C ABI expects a valid pointer.

Operations: `preset` (`name`: `basic`, `normal`, `full`); `session_accept` (`session_id`, `preset`, `accepted`, and for Full or sensitive custom flags `elevated_confirmed`); `session_check` (`session_id`, `capability`); `session_revoke` (`session_id`); `identity_generate`, `identity_sign`, `identity_verify` (binary fields are base64); `validate_input` and `inject_input` (`session_id`, `event`); `capabilities`. Custom accepts a `permissions` object using field names in `Permissions`. All omitted custom flags default false. Session state is in-process and disappears at restart. Revoke and checks must be wired to target-side dispatch, not merely called by a controller.

**Trust boundary:** Only trusted local target UI code may invoke acceptance or submit confirmation, select permissions, access private keys, and choose transfer directories. Never pass arbitrary peer JSON to this C ABI. Confirmation booleans do not themselves prove user interaction. Store private PKCS#8 keys in OS secure storage; never log or send them. The signing operation does not perform peer authentication or pinning. No unattended authentication is implemented. Full and sensitive custom settings require target confirmation; password verification is not implemented. The application must re-check authorization at each actual operation and establish authenticated encrypted transport before accepting remote input.

`file_begin` (`session_id`, `transfer_id`, target-selected `directory`, `filename`, `size`), `file_chunk` (`offset`, base64 `data` and `sha256`), and `file_finish` (base64 `sha256`) require file-transfer permission and bind transfers to a session. Revocation removes incomplete files. `FileReceiver` implements: exclusive-create, 1 GiB maximum, sequential chunks up to 256 KiB, per-chunk and final SHA-256; incomplete files are removed on drop. Directory selection is trusted and must not be remotely supplied. Disk quotas, transfers across restart, cancellation integration, and hardened directory-handle race protection are not implemented.

On Windows `inject_input` supports normalized absolute primary-screen mouse motion and left/right/middle buttons using SendInput; it is subject to Windows integrity restrictions and does not provide secure-desktop access. A limited virtual-key keyboard mapping and vertical wheel are supported; modifiers must be sent as separate key events. Touch injection is unsupported. Linux has an X11/XTest dynamic-loading implementation with primary-screen mouse, limited keys, buttons, and discrete 120-unit wheel steps. Wayland explicitly fails: no RemoteDesktop consent portal implementation exists. X11 requires a usable display and XTest extension; this build host has not compiled for or exercised a Linux target. Other platforms return an error. No device interaction was exercised in tests. There is no screen capture, WebRTC, clipboard, service, Android bridge, other TV protocol adapters, mDNS, direct-IP TLS/pinning/rate limiting, persistent trust, or deployment in this crate. Unsupported operations fail rather than reporting success. `capabilities` reports these omissions. Do not present this foundation as a working remote access product.

References: [Microsoft MOUSEINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-mouseinput), [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

Authentication primitives: the unattended password uses OPAQUE (RFC 9807, `opaque-ke`, Argon2id) through the `unattended_password_set` and `unattended_login_*` ops (see docs/AUTH_V2.md section 7), with a 12-character minimum; length alone does not ensure password strength. `key_fingerprint` and `check_pin` calculate SHA-256 fingerprints and require explicit confirmation on first use, and fail on mismatch. None creates a TLS listener or session. `auth::TrustedPolicies` is an in-memory policy map whose Ed25519 proof method verifies a domain-separated challenge; the caller must generate fresh random challenges, consume them once, protect persisted policy integrity, rate-limit attempts, and bind proof to the encrypted connection. Neither policy nor password primitives enable unattended access. Keep password and verifier operations local, and protect the verifier from tampering and brute-force attacks.

`tv::TvAdapter` exposes capability metadata, pair, keys, text, app launch, and state; unsupported operations return errors. Samsung and LG payload builders are protocol helpers only. The authorized bridge operations `samsung_key_payload` and `lg_request_payload` return `sent: false`; they neither open WebSockets nor confirm pairing or execution. A future transport must establish secure TV identity, implement pairing and response handling, and store TV tokens securely. LG registration builder requires a locally provided manifest. Vendor protocols are firmware-dependent. Sources: [Connect SDK webOS registration](https://github.com/ConnectSDK/Connect-SDK-Android-Core/blob/master/src/com/connectsdk/service/webos/WebOSTVServiceSocketClient.java) and [Samsung key reference](https://github.com/thomasnordquist/reference-implementations/blob/main/samsung-tv/KEYS.md).

Input wire schema uses `{ "t":"wheel", "dy":120 }` (nonzero integer, range -1200..1200), and `{ "t":"text", "text":"..." }` (nonempty, at most 16 KiB UTF-8). Native Windows and X11 injectors currently reject text. `sha256` hashes base64 `data` up to 256 KiB and returns base64 `sha256`. Sessions expire one hour after acceptance, are denied immediately on subsequent checks, and a background sweep removes sessions and partial transfers. Successful synthetic key/button downs are tracked and released on revoke, replacement, or expiry; `session_revoke` returns `release_failures`. OS failures can prevent release; synthetic releases can interact with concurrent physical input, and these paths have not been exercised on a real desktop. The expiry sweep may wait for an in-progress serialized native call.
