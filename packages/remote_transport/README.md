# Direct-IP signaling transport

Explicitly opt in with `DirectListener.start(enabled: true, ...)` after showing the owner an open-port warning. Supply an owner-provisioned TLS certificate/private key in `SecurityContext`, its SHA-256 DER fingerprint, and native-core-backed Ed25519 sign/verify and SHA-256 callbacks. The native `sha256` operation takes base64 `data` and returns base64 `result.sha256`. Never send private keys, passwords, or verifiers. Listener accepts one session at a time; target UI callback selects local permissions and confirms elevated access. Apply `session_accept` locally and enforce `session_check` at every operation. Full and any enabled custom permission require extra confirmation here. Close/revoke on disconnect and on local end.

The client uses an owner-selected numeric address/port. Persist both returned certificate and Ed25519 key fingerprints from `confirmPeer` in integrity-protected local storage only after explicit out-of-band comparison and confirmation; on later connections provide both pins. A changed pin fails closed; no silent re-pair. `enableFirstUse` permits a provisional TLS connection for unknown certificates, but no client identity or signature is sent until the separate local certificate approval callback succeeds. After mutual proofs, the client and target show the same comparison code concurrently; neither hands a session to the application until both have confirmed. The displayed 12-hex-digit comparison code binds both public keys, certificate fingerprint and fresh random nonces; the target sees it in its local acceptance callback. Pin fingerprint presentation and comparison must be implemented by the application. Callbacks must genuinely verify user interaction and use secure key storage.

The resulting session sends bounded JSON objects suitable for SDP/ICE signaling; caller validates message schemas, filters out TURN candidates/configuration, maintains an active-session indicator, and closes sessions. There is no TURN, router configuration, persistent trust, UI, WebRTC, or actual remote control in this package. Internet use requires owner-managed forwarding. This is a new protocol, not interoperable with the existing signaling server.

Failures after TLS handshake are limited to five per source per five minutes in memory; a single in-progress handshake/session blocks others. Dart's secure-server API does not expose failed TLS handshakes to this limiter: use OS firewall/network-level rate limiting as well. Restart resets limits. A caller must continuously read or explicitly close a session to observe disconnection and release the single-session slot. In-memory limits and timeout handling do not prevent network-level denial of service. A local loopback test exercises TLS and real Ed25519 proofs using Node crypto; no independent security audit or production interoperability test has been performed.

Dart TLS behavior: https://api.dart.dev/dart-io/SecureSocket/connect.html and https://api.dart.dev/dart-io/SecureServerSocket/bind.html.


The accepted preset and allowlisted custom permission flags are sent as controller-side metadata after consent. The controller never treats a peer-provided elevated-confirmation flag as target authorization; that confirmation remains local to the target.
