# Plan: Cross-Device Remote Control App (AnyDesk-style + Phone + TV)

## 1. Vision

A remote-access app like AnyDesk with two key extensions:

1. **Phone ↔ PC in both directions.** The phone can control a PC, and a PC can view and control an Android phone.
2. **TV control** from a phone or a PC: remote-style control (D-pad, volume, apps, keyboard) plus screen viewing where the platform allows it.

Everything works **over the internet**, not just on the same Wi-Fi.

## 2. Confirmed Decisions

| Area | Decision |
|---|---|
| Connectivity | Anywhere over the internet (LAN direct path used when available) |
| Accounts | None. Anonymous, ID-based connections only |
| Access control | Three presets (Basic, Normal, Full), customizable per device (see 10.1) |
| Hosting | Free, on Cloudflare: Workers signaling + Realtime STUN/TURN (see 5.1) |
| Direct-IP mode | Included: LAN, and internet with port forwarding (see 7.1) |
| TV bridge | Runs inside the PC/phone app; no standalone device |
| Android distribution | Direct APK first, Google Play later (see 6.5) |
| File transfer | Included in the first release |
| PC platforms | Windows and Linux |
| Phone platform | Android only |
| TVs | All major brands (via per-brand adapters) |
| TV control | Remote-style control and screen viewing |
| UI | Flutter, one codebase for Android and desktop |

## 3. Capability Matrix

| Controller ↓ / Target → | Windows PC | Linux PC | Android phone | TV |
|---|---|---|---|---|
| **Windows PC** | Yes | Yes | Yes (view + input) | Yes |
| **Linux PC** | Yes | Yes | Yes (view + input) | Yes |

## 4. Architecture

```
┌──────────────┐        ┌────────────────────────────┐        ┌──────────────┐
│  Controller  │◄──────►│  Signaling (CF Workers)    │◄──────►│    Target    │
│ (Flutter app)│  WSS   │  auth, presence, SDP/ICE   │  WSS   │ (Flutter app)│
└──────┬───────┘        └────────────────────────────┘        └──────┬───────┘
       │                                                              │
       │      WebRTC: video/audio track + data channels (input,       │
       │      clipboard, files, control)  — E2E encrypted (DTLS-SRTP) │
       └──────────────── direct (P2P) when possible ──────────────────┘
                         otherwise via TURN relay (Cloudflare TURN)

TV path:
Controller ──WebRTC──► Bridge (PC/phone app on TV's LAN) ──LAN protocol──► TV
```

Key idea: **WebRTC is the transport for everything.** Video goes as media tracks. Input events, clipboard, file transfer and TV commands travel over data channels.

## 5. Tech Stack

### Client apps
| Layer | Choice | Notes |
|---|---|---|
| UI | **Flutter** (Android, Windows, Linux) | One codebase |
| WebRTC | `flutter_webrtc` | Supports Android, Windows, Linux |
| Native core | **Rust** via `flutter_rust_bridge` | Input injection, TV adapters, crypto helpers, background agent logic |
| State management | Riverpod | |
| Local storage | SQLite (drift) + secure storage for keys | |

### Backend
| Component | Choice |
|---|---|
| Signaling API | **TypeScript on Cloudflare Workers** (WebSocket via Durable Objects) |
| Relay | **Cloudflare Realtime** (STUN/TURN) |
| Storage | Durable Object storage (or KV/D1) for device IDs and public keys |
| Presence | Held in the signaling Durable Objects (WebSocket connections) |
| Deployment | Wrangler (Cloudflare CLI); no servers to manage |
| Identity | No accounts: each device generates an ID and an Ed25519 keypair on first launch |

### Why this stack
- Flutter keeps the UI code single-source across all three client platforms.
- Rust handles the low-level, performance- and security-sensitive parts (input injection, protocol clients).
- Workers + Durable Objects handle many concurrent WebSocket connections with no server to maintain.
- Cloudflare Realtime provides global STUN/TURN with a free allowance, so there is no relay to run.

### 5.1 Hosting (free, on Cloudflare)

Hosting must cost nothing. Signaling is tiny; only the TURN relay uses real bandwidth, and most sessions should connect P2P and never touch it.

**Chosen setup**
- **Signaling:** Cloudflare Workers with Durable Objects (WebSockets, presence, handshake relay)
- **STUN:** Cloudflare STUN (free and unlimited)
- **TURN:** Cloudflare Realtime TURN (first 1,000 GB/month free, then $0.05/GB)
- Short-lived TURN credentials are generated by the Worker per session; the TURN key never ships in the app.

**Capacity note:** a relayed session at about 3 Mbps uses roughly 1.35 GB per hour, so 1,000 GB covers around 740 relayed session-hours per month. Only sessions where P2P fails are relayed.

**Guard against surprise bills**
- Cap relayed quality (lower bitrate/resolution) when a session is on TURN.
- Track relayed volume in the Worker and alert before the free allowance runs out.
- Optionally pause new relayed sessions near the limit.
- Check the current free-plan limits for Workers and Durable Objects before building.

**Fallback (if relay traffic outgrows the free tier):** self-run coturn on an Oracle Cloud Always Free VM (10 TB outbound/month; credit card at signup; idle instances can be reclaimed). Because the STUN/TURN server list is configuration sent to clients by signaling, TURN can move without an app update.

## 6. Components

### 6.1 Desktop Agent (Windows and Linux)
Runs as a background service with a tray icon, and also contains the controller UI.

**Windows**
- Capture: Windows.Graphics.Capture or DXGI Desktop Duplication
- Input: `SendInput`
- Run as a **Windows Service** plus a user-session helper so it can handle the login screen and UAC prompts (secure desktop)
- Hardware encoding: NVENC / QuickSync / AMF via WebRTC where available

**Linux**
- **X11**: XShm capture, XTest input
- **Wayland**: `xdg-desktop-portal` (ScreenCast + RemoteDesktop) with PipeWire; user consent prompt required by the portal
- Packaging: AppImage, `.deb`, Flatpak (the Flatpak sandbox works well with portals)

### 6.2 Android App (dual role)
**As controller**
- Touch gestures mapped to mouse actions (tap = click, two-finger scroll, long-press = right-click, pinch = zoom)
- On-screen keyboard and special keys bar (Ctrl, Alt, Esc, Win)
- Trackpad mode and direct-touch mode

**As target (phone being controlled)**
- Screen capture: `MediaProjection` in a foreground service
- Input: an **AccessibilityService** using `dispatchGesture` for taps, swipes and text input
- The user must explicitly grant both permissions, and a persistent notification shows an active session
- Limitation: some secure screens (banking apps, DRM content) block capture

### 6.3 Signaling Server
- Device registration and a short numeric ID (like AnyDesk) mapped to a device public key
- Presence (online/offline)
- Connection requests, accept/deny, and SDP/ICE exchange
- Issues short-lived TURN credentials
- Never sees media or input content (E2E encrypted)

### 6.4 TV Support
See section 8.

### 6.5 Android Distribution

1. **Start with a direct APK** for testing and early users: no review, and the full feature set including AccessibilityService control.
2. **Add Google Play later.** Play reviews AccessibilityService use closely, so check Google's current policy and permission declaration requirements first. A safe Play build is the controller and view-only features, with phone control (input injection) as an optional add-on or direct-APK-only component if it isn't approved.
3. **Always show a clear in-app disclosure** of what the accessibility permission does and when it is active, regardless of channel.

## 7. Connection Flow

1. Each device registers anonymously (ID + public key) and keeps an outbound WSS connection to signaling.
2. Controller enters the target's ID (or picks a saved device).
3. Target shows an **accept prompt**, or auto-accepts if unattended access is enabled and the controller is authorized.
4. SDP offer/answer and ICE candidates are exchanged through signaling.
5. WebRTC connects P2P, falling back to TURN when NAT blocks it.
6. Video track starts, and data channels open for input, clipboard and files.
7. Either side can end the session at any time; the target always has a visible "session active" indicator.

### 7.1 Direct-IP Mode

An optional second connection path that works without the Cloudflare signaling server.

- The target listens on a configurable port; the controller enters `IP:port`.
- **LAN:** works directly on the same network.
- **Internet:** works only if the owner forwards that port on their router (or the target has a public IP). UPnP port mapping can be offered as an option.
- The same WebRTC handshake runs over a direct TLS connection instead of Cloudflare signaling; no TURN is available in this mode.
- Same protections as ID mode: accept prompt, access presets, end-to-end encryption.
- With no server to vouch for the target, the controller pins the target's public key on first connect and shows a short confirmation code both sides can compare.
- **Off by default.** Turning it on shows a warning, and incoming attempts are rate-limited and blocked after repeated failures.

## 8. TV Control Design

### 8.1 Remote-style control: per-brand adapters
Each brand uses a different protocol, so build a common `TvAdapter` interface (`pair`, `sendKey`, `sendText`, `launchApp`, `getState`) with one implementation per brand:

| Brand / Platform | Control method |
|---|---|
| Android TV / Google TV | Android TV Remote Protocol v2 (TLS pairing with PIN) |
| Samsung (Tizen) | Samsung Smart TV WebSocket API |
| LG (webOS) | SSAP WebSocket API |
| Roku | External Control Protocol (HTTP, port 8060) |
| Amazon Fire TV | ADB over network and/or Android TV-style remote |
| Apple TV | Companion protocol (limited, community-reverse-engineered) |
| Vizio / others | Vendor APIs, added incrementally |

- **Discovery:** mDNS and SSDP on the local network.
- **Bridge model for internet use:** these protocols are LAN-only, so a device on the same network as the TV (a PC agent or the Android app) acts as a **bridge**. The remote controller sends commands over WebRTC to the bridge, which forwards them to the TV.
- Each brand adapter is isolated so brands can be added or fixed independently.

### 8.2 Viewing the TV screen
Support differs by platform, so tier it:

| Tier | Method | Coverage |
|---|---|---|
| A | **Companion app on the TV** captures the screen and streams over WebRTC | Android TV, Google TV, Fire TV (where capture is permitted) |
| B | ADB `screenrecord`/screencap via the bridge | Android-based TVs with ADB enabled |
| C | External HDMI capture device plugged into a PC | Any TV (hardware fallback) |
| D | Not available | Samsung, LG, Apple TV (no public screen-capture API) |

The UI should clearly show which features each paired TV supports.

## 9. Protocol Design

**Data channels**
- `input`: unreliable/unordered for mouse movement, reliable/ordered for clicks and keys
- `clipboard`: reliable text/image sync
- `files`: chunked transfer with checksums
- `control`: session settings (quality, monitor selection, permissions)
- `tv`: TV adapter commands and state

**Input message example**
```json
{ "t": "mouse_move", "x": 0.4213, "y": 0.7702 }
{ "t": "mouse_btn", "b": "left", "down": true }
{ "t": "key", "code": "KeyA", "down": true, "mods": ["ctrl"] }
{ "t": "touch", "id": 1, "phase": "move", "x": 0.31, "y": 0.62 }
{ "t": "tv_key", "key": "VOLUME_UP" }
```
Coordinates are normalized (0–1) so resolution differences are handled on the target.

**Video**
- Codecs: H.264 (hardware-friendly), VP8/VP9 fallback, AV1 later
- Adaptive bitrate and resolution via WebRTC congestion control
- Quality presets: Low latency, Balanced, High quality
- Multi-monitor selection on desktop targets
- Optional Opus audio streaming

## 10. Security Model

- **E2E encryption** through WebRTC DTLS-SRTP; signaling server cannot read sessions.
- **Device identity:** each device holds an Ed25519 keypair; controllers are authenticated against it.
- **No accounts:** access is gated by an accept prompt (attended) or a permanent password set by the owner (unattended). IDs are random and rate-limited against guessing.
- **Consent:** attended sessions need an explicit accept; unattended access needs a one-time setup with a strong password.
- **Permission levels per controller:** Basic, Normal, or Full preset (see 10.1).
- **Visible indicators:** tray icon, Android notification and an on-screen banner during sessions.
- **Safeguards:** rate limiting on connection attempts, ID-enumeration protection, session audit log, remote revoke of trusted devices.
- **TV pairing:** each bridge-to-TV pairing is stored locally in the bridge's secure storage.
- **TURN:** short-lived credentials only.

### 10.1 Access Modes

The target (or its owner) picks a preset when accepting a session or when saving a trusted device. It can be lowered or ended at any time during a session.

| Capability | Basic | Normal | Full |
|---|---|---|---|
| View screen | Yes | Yes | Yes |
| Mouse / keyboard / touch input | No | Yes | Yes |
| Clipboard | No | Text and images | Text, images, files |
| File transfer | No | No | Yes |
| Audio streaming | Yes | Yes | Yes |
| Power actions (lock, restart, shutdown, wake) | No | No | Yes |
| Elevated actions (UAC, login screen) | No | No | Yes |
| TV: remote keys (D-pad, volume, power) | No | Yes | Yes |
| TV: launch apps, text entry, ADB | No | No | Yes |
| Unattended access allowed | No | Optional | Optional, password required |

- Each preset maps to a set of permission flags enforced **on the target**, never trusted from the controller.
- **Full** always requires the owner's password or an explicit confirmation.
- The active preset is shown in the session banner and the tray/notification.

**Customization**
- Presets are templates over individual permission flags (view, input, clipboard text, clipboard files, file transfer, audio, lock, restart/shutdown/wake, elevated actions, TV keys, TV apps/ADB).
- The owner can start from any preset and toggle individual flags, saving the result as a **Custom** preset.
- Custom settings can be saved **per trusted device**, so one controller gets Basic and another gets a tailored Normal.
- Flags that grant elevated control (file transfer, power actions, elevated actions, ADB) still require the owner's password or explicit confirmation, even in a custom preset.
- Settings live on the target and are enforced there; a controller can only request access, never set it.
- "Reset to default" restores the original preset contents.
- The session banner shows **Custom** and lists the active flags on tap.

## 12. Build Phases

**Phase 1: Foundation**
- Signaling (Worker + Durable Objects), anonymous device IDs and keypairs
- Cloudflare Worker deployment and TURN credential setup
- Flutter app shell with WebRTC connection between two Windows machines (view only)

**Phase 2: PC ↔ PC control**
- Windows capture, input injection, clipboard
- Windows service plus session helper (login screen, UAC)
- Linux agent (X11 first, then Wayland portals)
- Attended/unattended access flows
- Access presets (Basic/Normal/Full) with per-device customization
- File transfer (Full mode)

**Phase 3: Phone as controller**
- Android controller UI (touch → mouse, keyboard bar)
- Phone → Windows/Linux sessions
- Quality presets and reconnect handling

**Phase 4: Phone as target**
- MediaProjection streaming
- AccessibilityService input
- PC → phone sessions

**Phase 5: TV remote control**
- `TvAdapter` interface, discovery, bridge mode
- Android TV, Samsung, LG, Roku adapters first
- Remote-control UI on phone and PC

**Phase 6: TV screen viewing**
- Android TV / Fire TV companion app (Tier A)
- ADB path (Tier B)
- Capability flags in UI

**Phase 7: Hardening and extras**
- Multi-monitor and audio
- Direct-IP mode (LAN first, then internet with port forwarding)
- Security review and audit logs
- Remaining TV brands, installers and auto-update

## 13. Risks and Constraints

| Risk | Mitigation |
|---|---|
| TURN relay bandwidth cost | Prefer P2P, cap relay quality, regional TURN |
| Wayland restricts capture and input | Use portals; accept the consent prompt; X11 fallback |
| Windows UAC/secure desktop | Run service as SYSTEM with session helper |
| Android blocks capture of secure content | Document limitation; show a placeholder |
| Android background kill and OEM battery limits | Foreground service, battery-optimization exemption guide |
| TV protocols are undocumented or change with firmware | Isolated adapters, versioned, community-maintained test list |
| Samsung/LG/Apple screen capture unavailable | Clear capability flags; HDMI capture fallback |
| Google Play policy on AccessibilityService | Clear disclosure and a core-functionality justification; offer sideload build |
| Misuse as remote-access abuse tool | Consent prompts, visible indicators, no hidden mode |
| Direct-IP mode exposes an open port | Off by default, warning on enable, rate limiting, key pinning, accept prompt |
